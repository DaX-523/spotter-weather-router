# Frontend — Agent Guide

Repo-wide standards live in `../AGENTS.md`. This file adds the frontend specifics.

## Stack

Vite 8 · React 19 · TypeScript (strict) · Tailwind CSS 4 · shadcn/ui (`base-nova` style on Base
UI, lucide icons) · TanStack Query 5 (server state) · React Router 8 (added with the second page)
· Leaflet + react-leaflet 5 (the map) · ESLint + Prettier · Vitest 5 + React Testing Library +
user-event (jsdom). Node 24 (`nvm use`).

## Commands (run in `frontend/`)

```sh
npm run dev            # http://localhost:5173; proxies /api to http://localhost:8000
npm test               # unit tests, single run
npm run test:watch     # tests in watch mode
npm run test:coverage  # tests + 90% coverage gate
npm run lint
npm run typecheck
npm run format
npm run check          # lint + format check + typecheck + coverage; must pass
npx shadcn@latest add button input card   # add shadcn/ui components
```

## Structure

```text
src/
  main.tsx       entry: mounts <App /> inside the providers (QueryClient, router). No logic.
  app/           the app shell and pages: thin, they compose components and call query hooks
  components/    app components grouped by area (components/trip-planner/), composed from ui/
    ui/          shadcn/ui primitives, generated by the shadcn CLI
    map/         the only place that imports Leaflet
  queries/       TanStack Query hooks around lib/api; query keys are built here and nowhere else
  lib/           framework-free logic: formatting, input validation,
                 URL-state parsing, risk → label/token mapping, map bounds
    api/         the only place that talks to the backend: the fetch client, one typed function
                 per endpoint, and types that mirror the /api/v1 contract
  test/          shared fixtures (realistic API payloads) and renderWithProviders
```

Tests sit next to the code they test: `format.ts` → `format.test.ts`, `route-card.tsx` →
`route-card.test.tsx`. Import through the `@/` alias (`@/lib/format`), not long relative paths.
Create a directory when the first module needs it.

## Data flow

- This is a single-page app. The browser calls our API under `/api/v1`. In development, Vite
  proxies `/api` to `http://localhost:8000`, so there is one origin and no CORS. `lib/api` builds
  URLs from `VITE_API_BASE_URL` (empty means same origin). How production serves the two is
  decided at deploy time.
- Never call third-party APIs (routing, weather, geocoding) from the browser. They go through the
  backend, which holds the keys. Map tiles are the one exception: their public tile URL and the
  attribution the tile provider's terms require are configured once, in `components/map/`.
- Server state lives in TanStack Query. There is no global store (Redux, Zustand) until a real
  need appears. Form state stays local to the form.
- The inputs that define a trip (origin, destination, departure time, load weight) live in the
  URL search params, so a plan survives a reload, can be shared, and works with the back button.
  A function in `lib/` parses them and drops anything invalid.
- Every query has a loading state, an error state and an empty state. An API error shows its
  `detail` message. When weather or routing data is unavailable (502/503), the UI says so and
  never presents a route as low risk.
- The backend ranks and explains routes; the UI shows that ranking and those reasons as they
  come. It never re-scores or re-sorts by risk.

## The map

- Leaflet draws with real browser layout and canvas or SVG, and it doesn't render meaningfully in
  jsdom. All map code stays in `components/map/` and is kept thin: it receives props that are
  already computed (route lines as `{ lat, lon }[]`, risk tokens, bounds) and draws them.
  Everything those props hold is computed in `lib/` and tested there.
- Tests of pages and components that contain the map mock `@/components/map` and assert on the
  props it receives.
- Our point type is `{ lat, lon }`. The conversion to Leaflet's `[lat, lng]` happens in one tested
  function in `components/map/`.

## Writing code

- Function components and hooks. Add state or effects only where a component needs them, and keep
  logic out of components: compute in `src/lib/` and unit test it there. Components render and
  wire up events.
- Type props explicitly and never use `any`. API request and response types are defined once, in
  `lib/api/types.ts`, not ad hoc in each component.
- Units: the API already speaks US units (`distance_mi`, `temperature_f`). `lib/format.ts` only
  formats them for display (rounding, unit labels), and components never do unit arithmetic.
- Make components accessible by default: semantic elements, labelled form controls, `<button>`
  for actions. Risk is never shown by colour alone: it always has a text label too, and an icon
  where one helps. The tests below depend on this.
- Layouts work at phone width first, since drivers will often open the app on a phone. Touch
  targets are at least 44px.
- Build UI from shadcn/ui components before writing your own. Add missing ones with the CLI
  rather than copying code from the web, so they match the configured style.
- shadcn/ui here sits on **Base UI, not Radix**: compose with the `render` prop, not Radix's
  `asChild`. Check the component's source in `src/components/ui/` before using its API.
- Treat `src/components/ui/` as generated: customize through variants, `className` and wrapper
  components in `src/components/`. It is excluded from coverage, so put no app logic there.
- Style with Tailwind utility classes and the theme tokens in `index.css` (`bg-primary`,
  `text-muted-foreground`), and merge classes with `cn()`. Don't hard-code colours, and that
  includes risk colours: they are theme tokens too.

## Writing tests

- Test what the user sees and does. Query by role, label or text
  (`screen.getByRole("button", { name: "Plan trip" })`); `getByTestId` is a last resort.
- Simulate interaction with `@testing-library/user-event` (`const user = userEvent.setup()`), not
  `fireEvent`.
- Assert with jest-dom matchers: `toBeInTheDocument`, `toHaveValue`, `toBeDisabled`, and so on.
- Never use the real network. Mock the API module (`vi.mock("@/lib/api")`) or stub `fetch` with
  `vi.stubGlobal`. Spies, stubbed globals and env vars are restored automatically between tests.
- Render anything that uses a query through `renderWithProviders` (`src/test/`). It creates a
  fresh `QueryClient` for each test with retries off. TanStack Query's default retries would
  otherwise make error-state tests slow and order-dependent.
- For time-dependent code, use `vi.useFakeTimers()` with `vi.setSystemTime(...)`, and call
  `vi.useRealTimers()` in `afterEach`.
- Wait for async UI with `findBy*` or `waitFor`, never with arbitrary delays.
- Compare computed numbers with `toBeCloseTo`, and assert on the formatted text the user sees.
- `main.tsx` is excluded from coverage, so it must stay free of logic.
